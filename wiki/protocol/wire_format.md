# Wire Format and Transport

- Transport: **Netty TCP** (default port **7001**) plus an optional **WebSocket** listener for browser clients (enabled by `MORGANA_WS_PORT` or `MorganaServerRuntime.start(webSocketPort = ...)`; one JSON packet per text frame, no length prefix; same TLS mode and connection gate as TCP). TCP port (`MorganaNettyServer.DEFAULT_PORT`; port 0 binds a free port in tests via `boundPort`).
- Framing: 4-byte length prefix (`LengthFieldBasedFrameDecoder`, max frame 2 MiB), then a UTF-8 string.
- Payload: **JSON** via `PacketCodec.encodeClientJson/decodeServerJson`, polymorphic discriminator field `pkt`. Packet names are prefixed `c_` (client) and `s_` (server).
- A CBOR codec (`encode*Cbor`) exists and is round-trip tested but is **not used on the wire** ([ADR 0009](/decisions/0009_json_wire_format.md)).
- The client queues incoming packets in a `ConcurrentLinkedQueue` for the render thread ([state and prediction](/client/client_state_and_prediction.md)).
- Ticking: a single-thread `ScheduledExecutorService` calls `coordinator.stepServerTick(50)` at a fixed 50 ms rate; exceptions are logged and the loop continues.
- **Protocol version & forward compatibility**: `PROTOCOL_VERSION` (currently 4) is sent in `Authenticate.protocolVersion` and echoed as `AuthResult.serverProtocolVersion`. A different or missing version (decodes as 0) is rejected before any account work with an "update your client" message. `ProtocolCapabilities` (`soft_seams`, `session_resume`, `realm_info`) are exchanged at login and resume for feature negotiation. Unknown server and client packets decode into ignorable `ServerPacket.Unknown` and `ClientPacket.Unknown` fallbacks without disconnecting. Bump the constant on breaking packet changes.
- **Packed maps** (protocol 4): every packet field that carries a `MapDefinition` (`MapStateSnapshot.activeMap` and `neighborMaps`, `MapDefinitionUpdated`, `SaveMapDefinition`) uses `PackedMapSerializer`: a **palette** of the distinct cells in first-appearance order plus **run-length** pairs `[count, paletteIndex, ...]` over the cells in row-major order, instead of every cell written out (JSON with defaults cost about 200 bytes per cell). Lossless and deterministic; code on both sides still handles plain `MapDefinition`s and the on-disk JSON is unchanged. Measured: a Hearthvale map 90,704 to 4,609 bytes; the hub snapshot with four neighbours 469,472 to 23,938 bytes; a noisy 256 x 256 map 231 KB, so the 256-tile limit now fits the 2 MiB frame cap. The decoder treats the packet as untrusted: size limits (5..256), run sums, positive counts and palette indices are checked before any cell list is allocated, and a bad map fails with a `SerializationException`. Tests: `PackedMapTest`.
- **Send-once map cache** (capability `map_cache`, additive, no version bump): the server remembers per connection which revision of each map it has sent (`mapRevisionsSent`; it dies with the connection, so a reconnect or resume starts clean). A `MapStateSnapshot` then lists `mapRefs` (`MapRef(id, revision)`, active map first, then neighbours) and carries `activeMap` / `neighborMaps` only for maps the connection does not hold at that revision; `activeMap` is null when it is already held. The client keeps a per-connection cache (`ClientWorldState`), rebuilds the snapshot's maps from it, caches every `MapDefinitionUpdated` (the server records those as sent to everyone), and clears the cache at each login. A revision always means the same content because live edits and hot reloads bump it. **Safety net**: if a ref cannot be resolved (missing or different revision) the client ignores that snapshot and sends `c_map_resync` (`RequestMapResync`); the server forgets what it sent and resends the current map in full, so a bad cache can never strand a player. Clients without the capability always get full maps. Measured in Chrome: the first snapshot is about 26 KB (active map plus four neighbours); after a map edit the snapshot is 2.6 KB. Tests: `MapCacheServerTest`, `MapCacheClientTest`.
- **Lean server JSON** (2026-11-17): `encodeServerJson` leaves out fields that hold their default value (about a third smaller, cheaper to encode). `AuthResult` and `ContentCatalogUpdated`, which carry content definitions, still write every field, and `s_auth_res` always names `serverProtocolVersion`. Consequence: changing the default of a field in a gameplay packet (or the runtime state it carries) changes what an older client reads, so treat it as a protocol change.
- **Cheaper sending** (2026-11-17): a broadcast to a map is JSON-encoded once and the text shared by every recipient (`ClientSession.sendEncoded`); the Netty session queues writes and flushes once per burst instead of once per packet; and one walking step sends each watcher one `PlayerUpdated` (the move and the character update used to send it twice). Measured on Halcyon Reach with 30 players walking on one map: tick 6.5 ms to 1.5 ms, 226 to 75 KB/s and 305 to 155 packets/s per player.
- **Not done: WebSocket compression.** `permessage-deflate` would shrink the login (271 KB, about 30 KB gzipped) and updates, but Netty 4.1.115's `WebSocketServerCompressionHandler` cannot cap decompressed size, so a client could send a small frame that inflates enormously. Wait for a Netty with `maxAllocation` support.
- **Encryption**: optional TLS wraps the connection below this framing, with no change to packets or `PROTOCOL_VERSION` ([TLS and invite codes](/server/tls.md)). With TLS off (the default for dedicated servers) frames are cleartext.
